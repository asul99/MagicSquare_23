# 마방진 과제 — `.cursorrules`(`tdd_rules`) 검토 보고서

**작성 목적:** `Reporter/03_magic-square-cursorrules-tdd-rules-report.md`에 정의된 `tdd_rules` YAML을 기준으로, 향후 `.cursorrules`에 넣을 때의 리스크를 네 가지 관점에서 점검한 결과를 기록한다.  
**범위:** YAML 문법, 필수 섹션 존재 여부, `forbidden`과의 잠재 충돌, 에이전트 준수 가능성(ai_behavior·상태 전이 포함). **수정안이나 초안 개편은 포함하지 않는다.**  
**검토 대상:** 워크스페이스에 `.cursorrules` 파일이 없었으므로, 03 보고서 §2의 `tdd_rules` 블록 및 동일 내용이 담긴 `Prompt/03_magic-square-cursorrules-tdd-rules-report-Prompting.md` 산출물을 SoT로 삼았다. `forbidden`·`ai_behavior` 원문은 저장소에 없어 해당 항목은 일부 검증 불가다.

---

## 1. YAML 문법

| 항목 | 결과 |
|------|------|
| 구조 | 최상위 `tdd_rules` 하위에 `red_phase` / `green_phase` / `refactor_phase`, 각 단계별 `summary`, 리스트 키(`steps`·`rules`·`coverage`·`proceed_when`), `next_phase`가 들여쓰기와 함께 일관되게 배치되어 **유효한 YAML 맵·시퀀스 구조로 판단**된다. |
| 특수 문자 | `proceed_when` 일부 문장에 **유니코드 곱따옴표**(`"` `"`)가 포함된다. 플레인 스칼라에서는 통상 파싱 오류는 아니나, 다른 에디터에서 ASCII 따옴표로 바꿔 붙일 때 혼동 여지가 있다. |
| 병합 시 주의 | 상위 문서가 YAML 전체가 아니거나(예: 마크다운), 들여쓰기·코드 펜스가 깨지면 오류가 난다. 이는 **조각 자체의 문법 결함**이라기보다 **삽입 위치·들여쓰기** 이슈다. |

**문제로 보고할 만한 문법 오류:** 상기 SoT 블록만으로는 **치명적 YAML 문법 오류는 확인되지 않았다.** (로컬에 PyYAML 등이 없어 기계 파싱은 수행하지 않았다.)

---

## 2. 누락된 필수 섹션

- 03 보고서는 **명시적으로 `tdd_rules` 블록만**을 범위로 하므로, 그 산출물만 놓고 보면 **`forbidden`·`ai_behavior`·프로젝트 메타 등 다른 키가 없는 것은 요구사항에 부합**한다.
- 반면 **“완성된 하나의 `.cursorrules` 파일”** 기준으로 팀이 정한 필수 섹션이 있다면, 그 템플릿은 본 저장소에 없어 **여기서 필수 섹션 누락 여부를 단정할 수 없다.**

---

## 3. `tdd_rules`와 `forbidden` 규칙 간 잠재 충돌

저장소에 `forbidden` 초안이 없어 **문장 단위 충돌은 검증 불가**다. 다만 이후 `forbidden`에 자주 넣는 규칙과 겹칠 때 **해석 충돌이 나기 쉬운 지점**은 다음과 같다.

| `tdd_rules` 측 | 잠재적 `forbidden` 유형 |
|----------------|-------------------------|
| **green_phase:** 이름 변경·추출·구조·**스타일 정리 금지** | “린트/포맷 항상 통과”, “경고는 즉시 제거” 등 → green 단계에서의 최소 수정 범위와 **긴장** |
| **red_phase:** 프로덕션 코드를 이 단계에서 작성·수정하지 않음 | 테스트 실행을 위한 최소 스텁 허용 여부는 **문장만으로 경계가 모호**할 수 있음 |
| **red_phase:** 의도된 테스트 실패 | “실패 빌드/실패 테스트 금지” 등 → **표면적으로** red 사이클과 모순처럼 읽힐 수 있음(단계 구분 문구로 완화 가능) |

---

## 4. Cursor AI가 실제로 일관되게 따르기 어려운 규칙

`.cursorrules`는 모델 지침일 뿐, **`next_phase`를 IDE가 상태 머신으로 집행하지 않는다.**

| 규칙 요소 | 이유 |
|-----------|------|
| `proceed_when` / `next_phase` | 세션 전체에서 red→green→refactor를 **강제 분리하지 않음**. 한 번의 응답에 테스트·구현·소규모 정리가 섞이기 쉽다. |
| red의 “프로덕션 코드 미수정” | 컴파일·실행을 위한 **최소 스텁**과의 경계가 모호하다. |
| refactor의 커버리지 조건 | “전 대비 낮아지지 않음(측정 가능한 경우)”은 **도구 실행과 수치 비교** 없이 모델이 스스로 증명하기 어렵다. |
| green의 “통과가 테스트 완화가 아닌 실제 구현에 의한 것” | **객관적 자가 판정**이 어렵고 해석 여지가 크다. |

---

## 5. 한 줄 요약

`tdd_rules` YAML 조각은 구조상 문제 없어 보이며, 03에서 정한 범위 밖 섹션 미포함은 의도된 설계다. `forbidden`·`ai_behavior` 원문이 없어 **충돌·행동 규칙 검증은 부분적으로만 가능**하고, **단계 전이·커버리지·‘완화 아님’ 판단**은 에이전트가 기계적으로 보장하기 어렵다. 원문이 준비되면 동일 체크리스트로 재검토하는 것을 권장한다.
