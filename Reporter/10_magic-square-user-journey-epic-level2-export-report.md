## EPIC — Business Goal

### Epic

**Invariant(불변조건) 기반 사고 훈련 시스템 구축**

4×4 Magic Square를 **도메인 문제**로 삼아, 소프트웨어 설계·테스트·구현을 **불변조건(Invariant)과 계약** 중심으로 반복 연습할 수 있는 훈련 체계를 만든다.

---

### 목적

| 구분 | 설명 |
|------|------|
| **Invariant 중심 설계** | 4×4 Magic Square의 규칙(행·열·대각선 합, 값 범위·중복 등)을 **도메인 불변조건**으로 명시하고, 설계·코드·테스트가 그 불변조건과 정합하는지를 훈련의 중심축으로 둔다. |
| **Dual-Track TDD** | **계약/속성(불변)** 쪽 테스트와 **예시·경계** 쪽 테스트를 구분해, 두 궤적을 동시에 다듬는 TDD 습관을 연습한다. |
| **입력·출력 계약** | 경계(boundary)와 유스케이스(control)에서 **입력 검증·오류 형태·반환 의미**를 문서·테스트와 일치시키고, “암묵적 동작”을 줄인다. |
| **설계 → 테스트 → 구현 → 리팩토링** | 작은 단위로 **설계(불변·인터페이스) → 실패하는 테스트 → 최소 구현 → 리팩토링** 사이클을 반복해, 일상적인 개발 리듬으로 체화한다. |

---

### 성공 기준 (Definition of Done — Epic)

1. **Domain logic 테스트 커버리지**  
   핵심 도메인 로직(마방진 규칙·상태 전이·순수 계산)에 대해 **라인/브랜치 기준 95% 이상** 커버리지를 달성하고, CI에서 측정·게이트로 사용한다.

2. **입력 검증 — 계약 테스트**  
   공개 API·경계에서 정의한 **입력 계약**(허용 범위, 금지 조합, 오류 타입)에 대해 **계약 테스트가 100% 통과**한다(의도된 실패 케이스 포함).

3. **하드코딩 금지**  
   규칙·한계·차원 등은 **이름 있는 상수·설정·도메인 값**으로만 표현하고, “특정 입력에 맞춘 분기만으로 통과시키는” 구현은 허용하지 않는다.

4. **매직 넘버 금지**  
   리터럴 숫자·문자열이 의미를 갖는 경우 **상수·열거형·설정**으로 끌어올리고, 리뷰·린트 규칙과 맞춘다.

5. **Invariant → Test 추적 가능**  
   각 불변조건(또는 계약 항목)에 대해 **대응 테스트(또는 명시적 테스트 이름·주석·문서 링크)**가 존재하고, 역으로 테스트에서 **어떤 Invariant를 검증하는지** 식별 가능해야 한다.

## Level 2 — User Journey (사용자 여정)

### Persona

| 역할 | 설명 |
|------|------|
| **소프트웨어 개발 학습자** | 4×4 Magic Square를 **도메인 연습 과제**로 삼아 설계·테스트·구현 역량을 쌓는다. |
| **TDD 훈련 중** | 실패하는 테스트부터 작성하고, 최소 구현·리팩토링 사이클을 **습관**으로 만들고자 한다. |
| **Clean Architecture 이해 중** | 경계(입력·출력)·유스케이스·도메인을 **역할별로 나누고**, 의존성 방향을 의식한다. |

---

### Journey

#### Step 1 — 문제 인식

목표가 **“마방진을 구현한다”**가 아니라, 다음으로 정의된다.

- **“4×4 Magic Square의 불변조건과 입·출력 계약을 만족하는 도메인을, 테스트와 함께 구축한다.”**  
  즉, “그림 그리기” 수준의 구현이 아니라 **규칙·경계·실패 의미**를 먼저 명확히 하는 문제로 인식한다.

---

#### Step 2 — 계약 정의

구현에 들어가기 전에 **경계에서의 약속**을 문서·테스트와 맞춘다.

| 항목 | 내용 |
|------|------|
| **입력 스키마 정의** | 격자 차원, 허용 값 범위, 빈칸 표현, 금지 조합(중복·범위 밖 등)을 구조화한다. |
| **출력 스키마 정의** | 완성 격자, 부분 해, “해 없음” 등 **성공·부분 성공·실패** 각각의 반환 형태를 정한다. |
| **예외 정책 정의** | 검증 실패, 불가능한 퍼즐, 내부 전제 위반 등에 대해 **어떤 오류 타입·메시지·HTTP/경계 매핑**(해당 시)을 쓸지 정책으로 고정한다. |

---

#### Step 3 — Domain 분리

단일 “마방진 클래스”가 아니라, **책임이 분리된 도메인 단위**로 나눈다.

| 구성 요소 | 역할 |
|-----------|------|
| **BlankFinder** | 빈칸 위치·개수 등 **격자에서의 공백**을 찾는다. |
| **MissingNumberFinder** | 주어진 제약 하에서 **채워야 할 후보·누락 값**을 도출한다. |
| **MagicSquareValidator** | 행·열·대각선 합, 값 범위·중복 등 **불변조건 충족 여부**를 검증한다. |
| **Solver** | 위 구성 요소를 조합해 **해를 탐색·완성**하는 흐름을 담당한다. |

---

#### Step 4 — Dual-Track 진행

UI와 로직을 **동시에** TDD 리듬으로 밀어 나간다.

| 단계 | 내용 |
|------|------|
| **UI RED / Logic RED 병렬** | 화면·API 등 **표현·경계** 쪽 실패 테스트와, **도메인·유스케이스** 쪽 실패 테스트를 병렬로 추가한다. |
| **GREEN 최소 구현** | 각 트랙에서 테스트를 통과시키는 **최소한의 코드**만 작성한다. |
| **REFACTOR 통합 정리** | 중복 제거, 이름·모듈 경계 정리, 공통 타입·검증 위치 조정으로 **두 트랙이 같은 계약·용어**를 쓰도록 맞춘다. |

---

#### Step 5 — 회귀 보호

기능 완료 후 **회귀 테스트**로 안정성을 확보한다.

| 유형 | 내용 |
|------|------|
| **엣지 케이스 추가** | 경계 값, 단일 빈칸·다중 빈칸, 이미 합이 맞는 부분 등 **극단 입력**을 테스트로 고정한다. |
| **입력 오류 케이스 추가** | 잘못된 차원, null/빈 입력, 타입 불일치, 계약 위반 입력에 대해 **정의한 예외 정책**이 지켜지는지 검증한다. |
| **조합 실패 케이스 추가** | Solver·Finder·Validator가 함께일 때 **해 없음·중간 실패·타임아웃**(해당 시) 등 **조합 단계에서의 실패**를 시나리오로 추가한다. |
