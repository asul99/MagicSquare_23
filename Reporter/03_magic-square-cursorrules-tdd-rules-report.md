# 마방진 과제 — `.cursorrules` TDD 규칙(`tdd_rules`) 정의 보고서

**작성 목적:** 에이전트·편집기 규칙에 넣을 Red–Green–Refactor 단계별 조건을 YAML로 정리해, 이후 `.cursorrules`에 그대로 병합하거나 참조할 수 있게 한다.  
**범위:** `tdd_rules` 블록만 정의한다. 프로젝트 전체 `.cursorrules` 초안이나 다른 섹션은 포함하지 않는다.  
**참고:** 워크스페이스에 `.cursorrules` 파일이 없을 수 있으므로, 본 문서가 해당 블록의 단일 출처(SoT) 역할을 할 수 있다.

---

## 1. 요약

| 단계 | 핵심 | 다음 단계로 넘어가는 조건 |
|------|------|---------------------------|
| **red** | 실패하는 테스트를 먼저 작성한다. | 의도된 실패가 확인되고, 실패가 구현 대상과 일치한다. |
| **green** | 통과에 필요한 최소 코드만 작성한다. | 관련 테스트가 통과한다. 이 단계에서는 리팩터링을 하지 않는다. |
| **refactor** | 동작은 유지하고 구조만 개선한다. | 테스트 전부 통과, 커버리지 약화 없음. 이후 새 기능은 다시 red부터. |

---

## 2. `tdd_rules` YAML 블록

아래를 `.cursorrules`의 적절한 위치에 들여쓰기를 맞춰 붙이면 된다.

```yaml
tdd_rules:
  red_phase:
    summary: 실패하는 테스트를 먼저 작성한다.
    steps:
      - 새 동작·버그 수정은 항상 실패하는 테스트로 시작한다.
      - 테스트는 구체적인 기대값·경계 조건을 포함한다.
      - 프로덕션 코드는 이 단계에서 작성·수정하지 않는다(테스트만 추가·수정).
    proceed_when:
      - 해당 테스트가 실행되며 실패한다(컴파일 오류가 아닌, 의도된 assertion/기대 실패).
      - 실패 원인이 “아직 구현되지 않음”과 일치한다(거짓 실패·환경 문제가 아님).
      - 실패 메시지가 다음 구현 대상을 명확히 가리킨다.
    next_phase: green_phase

  green_phase:
    summary: 테스트를 통과시키는 데 필요한 최소한의 프로덕션 코드만 작성한다.
    rules:
      - 목표는 오직 현재 실패 중인 테스트를 통과시키는 것이다.
      - 이 단계에서는 리팩터링을 하지 않는다(이름 변경, 추출, 구조 정리, 스타일 정리 금지).
      - 필요 이상의 일반화·추가 기능·사전 최적화를 하지 않는다.
      - 테스트를 약하게 만들거나 삭제하여 통과시키지 않는다.
    proceed_when:
      - 관련 테스트 스위트가 모두 통과한다.
      - 통과가 테스트 완화가 아닌 실제 구현에 의한 것이다.
    next_phase: refactor_phase

  refactor_phase:
    summary: 동작은 그대로 두고 구조만 개선한다.
    rules:
      - 관찰 가능한 동작·공개 API 시맨틱을 바꾸지 않는다.
      - 버그 수정·새 기능은 이 단계에 넣지 않는다(필요하면 red_phase로 돌아간다).
      - 중복 제거, 명명 개선, 모듈 경계 정리, 의존성 방향 정리 등 구조 개선만 수행한다.
    coverage:
      - 리팩터 전후로 동일 테스트가 통과해야 한다.
      - 기존 테스트로 커버되던 분기·경로가 약화되지 않도록 한다(필요 시 테스트 보강은 동작 동일 전제 하에서만).
      - 커버리지 지표는 리팩터 전 대비 낮아지지 않는 것을 조건으로 한다(측정 가능한 경우).
    proceed_when:
      - 전체 관련 테스트가 통과하고, 커버리지 조건을 만족한다.
      - 다음 기능은 다시 red_phase부터 시작한다.
    next_phase: red_phase
```

---

## 3. 적용 시 메모

- **YAML 들여쓰기:** 상위 문서가 2스페이스라면 `tdd_rules` 하위도 2스페이스로 맞춘다.
- **도구 연동:** Cursor 규칙이 YAML 전체를 파싱하지 않는 경우, 동일 내용을 불릿 규칙 문장으로 옮겨도 의미는 동일하다.
- **순환:** `next_phase`는 팀이 선호하는 문서화 방식이며, 실행기가 이 필드를 읽지 않아도 TDD 사이클 해석에는 문제 없다.
